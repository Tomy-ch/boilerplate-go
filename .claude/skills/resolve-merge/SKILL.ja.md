# Resolve Merge

衝突した各パスを、そのクラスが既に持っている解決へ振り分けてマージを着地させ、残りを差し戻す。

## 使うとき

- マージが衝突を報告したとき。
- マージが衝突を報告し**なかった**とき —— 派生生成物と連結生成物はそれでも再生成が要る。
- 手でマージを解決した結果、誰も編集していないファイルでゲートが落ちているとき。

以下には使わない: 実装コードの意味的衝突の解決、rebase / squash、誰も頼んでいないブランチの同期。

## 契約

| | |
| --- | --- |
| **所管** | 衝突パスのクラス分けと、クラスごとの機械的解決（再生成 / resolver 再実行 / 和集合 / 派生の再伝播） |
| **しないこと** | 実装の意味的衝突を解く / 生成物の片側を選ぶ / rebase・squash・force-push / レジストリの鍵衝突をどちらか採用する |
| **開始条件** | merge を実行した直後（衝突の有無を問わず） |
| **停止条件** | 機械的に解けないものが 1 つでも残ったとき — その場でマーカーを残して打ち切り、コミットしない |

## なぜ必要か

**このリポジトリでは、衝突マーカーの大半が誰も編集すべきでないファイルに落ちる。** `*.gen.go`、`*.sql.go`、
`*_mock.go`、`openapi.gen.yaml`、`database/gen/*.gen.sql`、生成された `docs/` ツリー、pin lockfile ——
どれも生成器か resolver を持っており、どれにも正しい「側」が無い。

そこで片側を選ぶと、選べる中で最悪の結果になる。マーカーが無く、レビューも通り、そして元から再現できない
ファイルができあがる。`gen-*-artifacts-check` ワークフローが後で、他人の PR で、その人が触ってもいない
コードの失敗としてそれを捕まえる。

2 つ目の理由はもっと静かである。**clean なマージは finished なマージではない。**
`database/gen/*.gen.sql` は DML ファイルの連結物であり、2 つのブランチがそれぞれ 1 ファイル追加すれば、
衝突は 1 つも起きないまま連結物だけが古くなる。書かれたものではなく導出されたものすべてに同じことが言える。
衝突で名付けられたスキルはまさにその場合に飛ばされる。だからこのスキルはマージで名付けられている。

## 引数

| 引数 | 効果 |
| --- | --- |
| `--base=<ref>` | ベースを解決せずこれを使う。hotfix 中は必須（Step 1） |
| `--class=<csv>` | 指定クラスに限定する。残りは報告して触らない |
| `--dry-run` | クラス分けと計画を報告する。何も変更しない |

## Step 1 — ベースを解決し、マージする

`CLAUDE.md` の Git Rules がこれを統べ、実行時に読む。ここでの正しさを決めるのはそのうち 2 つ:

- **PR の `baseRefName` が正である。** それがこのブランチが既にマージしていく先である。PR が無い場合に限り
  `make base-branch` が `origin` の実状態から現行のリリースラインを解決する。`refs/remotes/origin/HEAD` や
  `gh repo view --json defaultBranchRef` からベースを取ってはならない —— どちらも警告なく前のラインを答える。
- **rebase ではなく merge する。** `CLAUDE.md` の規則に加えて、ここでの rebase は追記専用ファイルを実際に
  壊す。同じ内容が両側で別ハッシュとして再着地し、独立した 2 つの追加として読まれる。

```bash
BASE=$(gh pr view --json baseRefName -q '.baseRefName' 2>/dev/null || make -s base-branch)
test -n "$BASE" || { echo "ベースを解決できませんでした"; exit 1; }
git fetch origin "$BASE"
git merge "origin/${BASE}"
```

マージするのはこのブランチが切られた元 —— PR のベース —— であって、今日いちばん新しいと解決されるものでは
ない。新しいリリースラインがその後開いていた場合、それをマージすることは追いつかせるのではなく振り替える
ことになる。

**hotfix ラインが絡むときは、何も解決せず聞く。** `make base-branch` は `release/*` しか見ないのでそれを
名指さないし、ブランチ名からベースを推測するのは、推測が最も高くつく瞬間に推測することである。人間から
`--base=<ref>` を要求する。

## Step 2 — 衝突した全パスをクラス分けする

```bash
git diff --name-only --diff-filter=U
```

| クラス | パス | 解決 |
| --- | --- | --- |
| 生成物 — Go / API | `**/*.gen.go`、`**/*.sql.go`、`**/*_mock.go`、`openapi/openapi.gen.yaml` | 両側を捨てる。`make gen-api` / `make gen-query` |
| 生成物 — DML 連結 | `database/gen/*.gen.sql` | `make merge-dml` → `make gen-sqlc`。**衝突していなくても走る** |
| 生成物 — docs | `docs/openapi/**`、`docs/godoc/**`、`docs/db-schema/**`、`docs/coverage/**`、`docs/portal/guides/**`、`docs/portal/docs.json` | 再生成する。feature PR には入れない —— release push のワークフローが同期する |
| pin lockfile | `.github/actions-pin.toml`、`docker/images-pin.toml` | 行を選ばない。`make pin-actions-resolve` + `make pin-actions-apply`、`make pin-images-resolve` + `make pin-images-apply` |
| バージョン派生 | `go.mod` の `go` 行、Dockerfile の `FROM`、README に書かれた版 | 正本は `mise.toml`。まずそちらを決着させ、`make sync-versions` |
| vendor | `vendor/**` | 未追跡。`go mod vendor` |
| 追記専用レジストリ | `docs/adr/README.md` の表、`docs/spec/glossary.md`、`.agents/ddd-audit/pattern-ledger.yaml` | 両側のエントリを和集合にする —— ただし同じ鍵が両側にあれば Step 6 が差し戻す |
| マイグレーション | `database/migrations/**` | 既存のマイグレーションを編集しない（`CLAUDE.md`）。番号衝突は新しい側だけ採番し直す |
| 対訳ペア | `**/*.ja.md` | 先に英語 canonical を解決し、`canonicalize-doc` で再同期する。`.ja.md` を直接解決しない |
| 実体化された env | `env/.env` | そもそもコミットしない（`repo-ops` §7） |
| 実装 | それ以外すべて | **機械的ではない。** マーカーを残したまま差し戻す |

何かを解決する前にクラス分けする。どの行にも当たらないパスは既定で実装である —— 安全な向きはこちらである。
機械的なものを差し戻すコストはメッセージ 1 つ、意味的なものを機械的に「解決」するコストは静かに誤ったマージ
だからである。

## Step 3 — クラス順に適用する

依存順に解決する。複数のクラスが互いを供給しているためである: `mise.toml` は `sync-versions` の前、
マイグレーションは `merge-dml` の前、DML は `gen-sqlc` の前、OpenAPI の元は `gen-api` の前。

生成物クラスではどれも同じ動きで、はっきり述べる価値がある。**ファイルをマージするのではなく、衝突を消して
作り直す。** 両側から正本を取り —— マイグレーション集合、DML ファイル群、`openapi/openapi.yaml`、
`mise.toml` —— *そちら*が衝突していれば解決し、そのうえで生成器を回して生成物を作らせる。

pin lockfile はエントリを突き合わせるのではなく resolver を回す。lockfile は tag → SHA のキャッシュであり、
手でマージすると、その tag に一度も対応したことのない SHA を持つエントリが残りうる。以後のすべての検査は
それを権威として扱う。

## Step 4 — 衝突しなかったものを再生成する

Step 2 が何も見つけなかったかどうかに関わらずこれを回し、回したと述べる:

```bash
make merge-dml && make gen-sqlc     # database/gen/*.gen.sql は連結物
make gen-api                        # OpenAPI 由来のコードと mock
make sync-versions                  # mise.toml → go.mod / Dockerfile / README
```

派生生成物が古くなるのは、*相手側*の変更によってであって、相手とのテキスト上の衝突によってではない。ここが
抜けると、ローカルは緑のマージ、次の無関係な PR で CI が赤、という結果になる。

## Step 5 — 検証する

```bash
make pin-actions-check && make pin-images-check
make check-migration-up-version && make check-migration-down-version
make check-migration-up-gap && make check-migration-down-gap
make md-doc-ref-lint && make md-skill-lint
make go-lint && make go-test
```

`make go-lint` / `make go-test` は、このリポジトリのローカルゲート負荷帯によっては CI へ委譲されうる。全部回った
かのように書かず、実際に回したゲートを述べること。

## Step 6 — 終わり方は 2 通り

実行はちょうど 2 つの状態のどちらかで終わる。どちらになるかは、機械的でないものが残っているかだけで決まり、
どれだけ解決できたかでは決まらない。

### 何か残った → そこで止める

残っているものを、衝突マーカーを**残したまま**報告し、実行を終える:

| 人間に残すもの | 理由 |
| --- | --- |
| 実装の衝突 | どちらの挙動が正しいかは読解であってマージではない |
| 同じ鍵が両側に追加された —— ADR 番号、用語、台帳のパターン | 和集合は機械的だが、どちらの定義が残るかの決定は機械的でない |
| ADR の採番し直し | 採番規約は `docs/adr/README.md` のものである。実行時に読み、それと現行運用が食い違うなら、選ばずに `CLAUDE.md` の *Conflicting Authority* に従って提起する |
| ベースを 1 つの ref に解決できなかった | ベースを推測することが、ブランチが黙って誤ったラインへマージされる経路である |

> 機械的に解けるところまで統合しました。残りはここからお願いします: `<path>`（実装の意味的衝突）…

**この状態ではコミットしないし、しようかとも聞かない。** 衝突マーカーを抱えた merge commit は履歴に入った
壊れたツリーであり、しかも解決済みに読める壊れ方をしている —— このスキルが防ぐために存在する失敗が、1 つ上の
層で起きた形である。止まった場所から人間が続けられるよう作業ツリーをそのまま残すこと。そして相手が残りを
解決した後に「仕上げ」に戻らないこと。それは相手のコミットである。

### 何も残らなかった → 聞いてから、コミットしてプッシュ

すべての衝突が解決され、Step 5 のゲートが緑のときに限って:

```text
質問: マージ元との統合が完了しました。コミットしてプッシュしますか？
選択肢:
  - コミットしてプッシュ
  - コミットのみ（プッシュしない）
  - 何もしない（作業ツリーのまま）
```

**毎回聞くこと。マージが成功したことを根拠にプッシュしない。** ブランチがリリースラインを取り込みつつ、その
マージがマシンの外へ出てよい状態ではない、ということはありうる。そしてこのスキルにはその区別がつかない ——
結果がリモートへ届くべきかはブランチの状態についての話であり、それは著者の知識であってマージの知識ではない。

プッシュの側については、ブランチに既に PR があるとき `CLAUDE.md` が確認とその文面を要求している:

> 変更はローカルにコミット済みです。これらの変更をプルリクエストにプッシュしますか？

コミットそのものは `commit` へ委譲する。あちらがリポジトリの規約で分割し、文面を作る。

## やること / やらないこと

- ✅ ベースは PR の `baseRefName` から取る。hotfix ラインが絡むときは `--base` を要求する。
- ✅ 何かを解決する前に、衝突した全パスをクラス分けする。
- ✅ 生成物は片側を選ばず、元から作り直す。
- ✅ pin lockfile は resolver を回す。バージョン派生は `sync-versions` で伝播させる。
- ✅ 何も衝突しなくても派生生成物を再生成し、そうしたと述べる。
- ✅ どの行にも当たらないパスは実装として扱う。
- ✅ 実際に回したゲートを述べる。
- ✅ ちょうど 2 つの状態のどちらかで終える。clean な側ならコミット前に聞く。
- ✅ 日本語で報告する。
- ❌ 生成物・lockfile・`.ja.md` を手で編集する、片側を選ぶ。
- ❌ rebase、squash、force-push、そのブランチのベース以外のラインをマージする。
- ❌ 既存のマイグレーションを編集する、番号衝突の古い側を採番し直す。
- ❌ 両側で衝突したレジストリの鍵のどちらが残るかを決める。
- ❌ 実装コードの意味的衝突を解決する。
- ❌ 衝突マーカーが 1 つでも残っている状態でコミットする、あるいはコミットを申し出る。
- ❌ マージが成功したからプッシュする —— ブランチが出せる状態かは著者の知識であってマージの知識ではない。

## チェックリスト

- [ ] ベースを PR の `baseRefName` から解決した、または `--base` で受け取った。rebase ではなく merge した。
- [ ] 衝突した全パスをクラス分けした。当たらないパスは実装として扱った。
- [ ] 生成物は片側選択ではなく元から作り直した。
- [ ] pin lockfile を resolver で解き直した。バージョンを `mise.toml` から伝播させた。
- [ ] レジストリを和集合にした。衝突した鍵は決めずに差し戻した。
- [ ] `.ja.md` より先に英語 canonical を解決し、そのうえで再同期した。
- [ ] Step 4 の再生成を衝突件数に関わらず回し、そう述べた。
- [ ] ゲートを回して名指した。委譲したものは委譲したと述べた。
- [ ] ちょうど 2 つの状態のどちらかで終えた。
- [ ] 何か残った → マーカーそのまま、何もコミットせず、何も申し出ず、実行を止めた。
- [ ] 何も残らなかった → コミット / プッシュを聞いた。前提にしなかった。コミット自体は `commit` に任せた。
