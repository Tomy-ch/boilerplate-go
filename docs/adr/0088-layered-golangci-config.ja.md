# ADR-0088: golangci 設定を層に分ける——誰がどの頻度で回すかで割る

## ステータス

accepted

## 背景

golangci-lint は `--config` が無いとき `.golangci.yaml` を自動で拾うため、`--config` を渡さない者——
エディタ統合、素の CLI 実行、我々が管理しない誰かのツール——はそのファイルが持っているものを得ます。
権威ある規則集合は、保存ごとの pass が許容できるものよりはるかに厳しいです——リンターは約 20 に対して 50 以上、層境界を守る `depguard` の全ルール、そして
`forbidigo` のパターンです。この解析には分単位の時間がかかります——開発機が空いていて 2.5 分、並行
worktree がホストを埋めているときで 17.5 分の実測に対し、最小構成の予算は 30 秒です。

その後、消費者がもう 1 つ現れました。リポジトリ内で作業する AI エージェントで、保存ごとではなく
チェックポイントで lint を回します。そのライフサイクルは他の 2 つのどちらとも違います。エディタの
pass は保存ごとで対象は 1 パッケージなので、1 秒を超えてはならず、いま目の前のファイルで著者が
対処できるものだけを報告すべきです。エージェントの pass は意図的でリポジトリ全体が対象なので、秒
単位を許容でき、広さを求めます。1 つのファイルで両方を賄うと、どちらかにとって誤った選択を強いる
ことになり、しかもその失敗は静かです——チェックポイント用に共有ファイルを強化すると、保存ごとに
発火するものまで変わります。

権威との違いはリンターの速度ではありません。**full ゲートはマージ前に必ず走る**以上、早い pass が
存在価値を得るのは「**遅く見つかると直すコストが高いもの**」を捕まえるときだけ、という点にあります。
向きを誤った層境界はパッケージの移動か依存の反転を意味しますが、禁止された `time.Now` は既に注入
されている `clock.Clock` への 1 行の差し替えです。どちらも CI で落ちますが、そこで見つかって痛いのは
前者だけです。

## 決定

golangci-lint の設定を 3 つ維持し、それぞれを「どの pass が回すか」で名付けます。

- `.golangci.yaml` —— 権威あるゲート。`make go-lint` / `make go-fix` と CI が回します。`depguard` の全
  ルールと `forbidigo` のパターンを含む完全な集合を持ちます。暗黙探索の名前を持つのは意図的です——
  `--config` を渡さないツールは**最も厳しい**集合を得るので、設定されていない実行が、ゲートなら
  拒否するものを緑と報告することがありません。
- `.golangci-min.yaml` —— 保存ごとの pass。`.vscode/settings.json` が `go.lintFlags` で明示的に
  指します。厳選した最小構成で固定 30 秒の timeout を持ちます。次のキーストロークより長く生きる
  保存時 pass は、pass が無いより悪いためです。**これはゲートではありません。** 強制を目的として
  何かを足してはいけません。
- `.golangci-fast.yaml` —— チェックポイントの pass。`make go-lint-fast` が回します。違反が波及する
  `depguard` ルール——層境界、依存の向き、共有パッケージの独立性——を持ちます。これもゲートでは
  ありません。変更が誤った形で作られていることを知る、最も安い場所です。
どの入口も `--config` を明示的に渡すので、暗黙探索は機構ではなく安全網です。
強制されねばならない規則は、他所にも現れるかどうかに関わらず `.golangci.yaml` に属します。
3 つは包含関係で並びます。

```txt
.golangci-min.yaml  ⊆  .golangci-fast.yaml  ⊆  .golangci.yaml
```

それぞれは次を派生させたものではなく自分の pass のために選ばれているので、自動で伝播するものは
ありません。しかしこの順序は 2 つの意味で保たれねばなりません。狭いファイルにあるリンターや
`depguard` ルールは、より広いすべてのファイルにも在ること。そして複数のファイルに現れる規則は、
狭い側で**より厳しく**なってはならないこと——早い pass は `deny` を省いてよいが、ゲートに無いものを
足してはいけません。ゲートが受け入れるものを早い pass が報告するなら、それは存在しない規則を教えて
いることになります。

宣言された例外が 1 つあります。欠陥ではなく**意図的で一時的な状態**を報告するリンターは、早い pass に
属し、ゲートには入れてはいけません。今日の唯一の該当は `godox` です——`arch-check` が人間に解決を委ねる
ために書き込む `// TODO:` ハンドオフコメントを可視化するものなので、ゲートにするとこのリポジトリが
同梱するワークフローの直後に CI が落ちます。この例外に加えるには同じ論証が要ります——そのリンターの
指摘が欠陥ではない、というヒントであることです。

固定 timeout を持つのはエディタ用の設定だけです。リポジトリ全体を回す pass の所要はリポジトリと共に
伸びるため、設定に書いた予算は陳腐化します。打ち切りはそれを回す入口が持ちます——ローカルでは
makefile の `GOLANGCI_LINT_TIMEOUT`、CI では `go-lint` ジョブの `timeout-minutes` です。

## 影響

### ポジティブな影響

- 各 pass が自分のコスト上限に合わせて調整されます。エディタは応答性を保ち、チェックポイントの pass は
  回す価値を保ち、CI の強制は曖昧さがありません。
- チェックポイントの pass を強化しても、保存ごとに発火するものは変わらなくなりました。
- 層境界のルールが CI より前にエージェントと著者へ届きます。そこが安い場所です。

### ネガティブな影響

- 維持するファイルが 3 つになり、包含の順序は現時点で何も強制していません。早い側は実際にゲートから
  静かに乖離したことがあり、それも共有していた規則の**本文**の中で起きました。順序を検査するものが
  入るまで、乖離は人が読んで見つけることになります。
- full ゲートに足した規則は、意図的に足さない限りエディタにもチェックポイントにも現れません。これは
  選択であることの意図されたコストであって、全部を同期して直すべき見落としではありません。

## 検討した代替案

### 単一の共有設定

どこでも 1 つの `.golangci.yaml` を使う案。維持は簡単ですが選択を強います——エディタとチェックポイント
の双方で完全な低速スイートを使うか、CI を高速な部分集合まで弱めるかです。どちらも受け入れられません。

### 2 つの設定（エディタとゲート）

この記録が元々述べていた構成です。CI 以外の消費者がエディタだけだった間は十分でした。チェックポイント
の pass が現れた時点で十分でなくなりました。両者はコスト上限も「有用な指摘とは何か」の定義も共有せず、
共有ファイルは直近に編集した側だけに静かに奉仕するためです。

### golangci-lint の `--fast` フラグ

`--fast` はリンターの部分集合を選びます。プロジェクト固有の `depguard` ルールを選択的に強制するために
必要な粒度の制御を与えず、フラグの意味はバージョンをまたいで変わってきました。

## 補足

- 出所: `.golangci-min.yaml`（エディタ）、`.golangci-fast.yaml`（チェックポイント）、
  `.golangci.yaml`（ゲート）、および `.makefiles/go/golangci-lint.mk` の `lint` / `fix` ターゲット。
- `.golangci.yaml` の `depguard` ルールは、[`docs/rules.md`](../rules.ja.md) が文書化している
  層の依存ルールを機械で強制した表現です。
- 関連: [ADR-0002](0002-onion-architecture.ja.md) —— `depguard` が強制する層境界。
