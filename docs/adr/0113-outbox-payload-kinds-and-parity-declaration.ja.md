# ADR-0113: outbox payload の種別を宣言させ、snapshot はフィールド対応を検査する

## Status

accepted

## Context

outbox の payload は、それを発行する usecase の隣で一度書かれ、その後はこのリポジトリが所有しない
購読側から永く読まれ続ける。写し元の集約のほうは変わり続ける。

この 2 つを繋ぐものが何も無かった。集約にフィールドが増えても payload はそのままで、その対を見る検査は
リポジトリのどこにも無い。この記録を生んだ失敗は、その隙間が実際に取る形そのものである。
`purchase.created.v1` は集約に値引きを得たが payload には得ず、payload の数字を足し合わせた購読側は
`subtotal + tax + shipping ≠ total` を見ることになった。**あらゆる層のレビューがこれを通した** —
単体テストは在るフィールドだけを assert し、レビュアーはコードとコードを突き合わせ、実 HTTP は
レスポンス DTO が正しかったので正しい応答を返した。露見したのは `outbox` の行を直接読んだときだけだった。

素直な規則は効かない。**どの payload も doc コメントで自分を「自己完結 snapshot」と呼んでいた**ので、
その語では集約の状態を負う payload と負わない payload を分けられない。`purchase.paid.v1` は集約の
17 フィールドのうち 5 つしか運ばないが、それで正しい — 支払いが起きたこと、どの購入か、いつかを報せる
payload だからである。全フィールドを要求する検査は、8 つのうち 6 つを「あるべき姿であること」を理由に
落としていた。

したがって問うべきは「この payload は全部運んでいるか」ではなく **この payload は何を約束したのか**
であり、それはコードからは導けない。発行する層が下す判断であり、その層はすでにワイヤ表現を所有している
— 事象の名前はドメインが持ち、その表現は持たない（`internal/domain/README.md` の Domain events）。

## Decision

**すべての outbox payload は自身の種別を宣言し、`snapshot` はさらに写し元の集約の全フィールドを
分類する。** 宣言は payload を組み立てる `Build*` の隣の `payload_parity.yaml` に置き、
`TestOutboxPayloadParity` がコードと突き合わせる。

| 種別 | 約束すること | 義務 |
| --- | --- | --- |
| `snapshot` | 事実が起きた時点の集約の状態。購読側が問い合わせ返さずに済む | 写し元 struct の全フィールドを、運ぶ（JSON 名を書く）か運ばない（理由を書く）に分類する |
| `notification` | 何が・いつ・どの識別子に起きたか | フィールド単位の義務は無い。宣言そのものが「この payload は集約を追随しない」という記録になる |

検査は突き合わせるすべての集合を双方向で読む。`Build*` を持つのに宣言の無いパッケージは落ち、
`Build*` の無い宣言も落ちる。宣言に無い payload は落ち、実体の無くなった宣言も落ちる。`snapshot` では、
未分類の集約フィールドが落ち、集約から消えたフィールドの宣言も落ちる。

**強制されるのは「判断が記録されたこと」であって、どちらの判断かではない。** 集約にフィールドを足すと、
その payload が運ぶかどうかを誰かが書き下すまで赤になり、どちらの答えでも検査は通る。仕掛けはこれだけで
ある — 失敗の型は「誤った選択」ではなく、そもそも「誰も選択を求められなかった」ことだった。

フィールドが内訳を成す `snapshot`（購読側が足し合わせることを期待される金額など）は、算術も自分の
単体テストで全項を非 0 にして固定する。フィールド単位の対応が示すのは項目が在ることまでで、
それらが依然として噛み合っているかは算術でしか示せない。`purchase.created.v1` が壊れたのはまさにそこ
だった。

意図的に対象外とする形が 2 つある。検査は写し元 struct の**トップレベル**しか読まないので、値オブジェクトの
内側の判断はその値オブジェクトに留まる。そして検査は**一方向**である。payload が他所（別の集約や派生値）
由来のフィールドを宣言なしに持つことは許す。この記録が扱う危険は「集約が payload の足元から動く」ことで
あって、payload が増えることではない。

## Consequences

### Positive

- この記録を生んだ失敗が、集約が変わったその瞬間に赤いテストとして現れる。しばらく後に購読側の帳簿で
  数字が合わない形ではなく。
- 2 つの archetype がコード上で分離される。`notification` は不在ではなく表明された立場になるので、
  薄い payload を読むたびに例外として弁護する必要が無くなる。
- 宣言は説明する対象の隣に置かれ網羅的なので、陳腐化すると落ちる。腐っても黙っている allowlist との
  違いはそこにある（`internal/architest/README.md` の Notes）。
- このテンプレートから作られサンプル API を撤去したプロジェクトでも、ゲートは残る。宣言はサンプルの
  パッケージと一緒に消え、検査は対象 0 件を許容し、利用者が最初に書いた `Build*` が宣言されるまで落ちる。

### Negative

- 集約にフィールドを足すのに 2 つ目のファイルを編集することになる。これは意図したコスト
  （その編集こそが記録される判断である）だが、実コストであり、outbox と無関係な変更にも降りかかる。
- 検査は gofmt 済みソースのテキスト走査である（`depguard` がここでの `go/ast` を禁じるため）。
  解析できないフィールドの形（埋め込み、複数名宣言）は読み飛ばさず未分類として報告するので安全側だが、
  そうした形を意図して導入すると騒がしくなる。
- `payload_parity.yaml` は、Go パッケージの中に置く非 Go の宣言ファイルとしてこのリポジトリで初めての
  ものである。説明する payload の隣にあるのは自然だが、新しい前例ではある。

### Neutral

- ワイヤ表現は何も変わらない。既存の購読側が見る payload は同じで、例外は `purchase.created.v1` が
  `orderedAt` を得たことだけ — これは追加であり、以前欠けていたのは発行側が DB の刻印前の集約を
  渡していたからにすぎない。
- payload の doc コメントから「自己完結」の語を退けた。誤っていたというより、何も区別できなかった。
