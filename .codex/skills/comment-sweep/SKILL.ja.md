# コメント清掃

これはコメント削除ではなく、移設と集約のワークフローである。コメントの分量を蒸し返さないこと。非自明で検証可能な Why には、残す具体的な根拠がある。代わりに、実行時の権威が定める管轄の問いを立てる。この判断が覆されたとき、更新が必要になるのはどの文書か。どれも必要にならないなら、管轄はコードであり、コメントはそのまま残る。

findings・選択肢・提案する文面・要約を含め、ユーザーに見えるすべての出力は日本語でなければならない。

## 実行時の権威

選択したスコープを読む前に、以下の各出典を読むこと。記憶した方針をハードコードしたり代用したりしないこと。このスキルと食い違う場合は `docs/rules.md` が勝つ。

| 問い | 実行時の出典 |
| --- | --- |
| 許容されるコメントの内容と管轄 | `docs/rules.md` の *Comment Rules* |
| 移設先の種別 | `docs/adr/README.md` の *What belongs here* |
| サブシステムの設計リファレンス | `docs/design/README.md` |
| パッケージのスコープ | そのパッケージの最も近い祖先の `README.md` |

監査を行う前、または監査役へ委譲する前に [`references/audit-prompt.md`](references/audit-prompt.md) を読むこと。これが全監査役に共通する唯一の指示ファイルである。

## 1. スコープと適用モードを確認する

対象ファイルを読む前に、次の2つの番号付き質問を日本語で提示し、ユーザーの選択を待つ。フラグまたは呼び出し元が一方を固定済みなら、その質問を省く。両方が固定済みなら、どちらも質問しない。

スコープ:

1. 指定パス配下（パッケージまたはディレクトリ）
2. ベースブランチとの差分
3. レイヤ全体（`internal/domain`、`internal/usecase`、`internal/controller`、`internal/infrastructure`、`pkg`）
4. キャンセル

適用モード:

1. 確認して適用（既定。1 件ずつ確認してから書き換える）
2. 自動適用（確認なしで適用可能な findings を書き換える）
3. 報告のみ（書き込まず、全 findings を報告する）

`--apply` は自動適用に、`--report-only` は報告のみにモードを固定する。両フラグが指定された場合は、互いに矛盾する旨を日本語で述べてモード質問に戻る。暗黙の優先順位を選ばないこと。

在庫（stock）スコープがこのスキルの目的である。差分スコープが選ばれた場合は、通常は `comment-reviewer` のほうが適した道具であり、この清掃では変更行だけでなく変更されたファイルのコメント在庫全体を判定する旨を日本語1行で述べて続行する。キャンセルなら対象スコープを読まずに止める。

## 2. 対象を解決し順位付ける

選択したスコープ配下のソースファイルをすべて解決する。`*.gen.go` / `*.sql.go` / `*_mock.go` / `*_test.go` は除外する。スコープ内にあれば、シェル・Dockerfile・Makefile・SQL・YAML・`.mjs` などの非 Go ソースも含める。それらの散文も同じ基準に従い、`revive` の守備範囲ではない。

コメント行を数え、分量の多い順にファイルを並べ、その順位を日本語で示す。ファイルはパッケージディレクトリごとにまとめる。監査の単位がパッケージなのは、その最も近い README が管轄上の移設先になり得るからである。

## 3. 二段階で読み取り専用監査を行う

ランタイムが並列検査に対応しているなら、独立したパッケージ群を並行して監査する。対応していなければ順に監査する。各監査役は次を満たさなければならない。

- 厳密に読み取り専用であること。証拠・判定・着地形だけを提示し、ユーザーへ問うことも書き込むことも決してしない。
- 言い換えた委譲プロンプトではなく、`references/audit-prompt.md` を逐語で読んで従うこと。
- 実行時の権威と、そのパッケージの最も近い README を読むこと。
- 個々のコメントすべてに Pass 1 を実施した後、全ファイルをまたぐ担当パッケージのコメント全体を一つのまとまりとして Pass 2 を実施すること。

Pass 1 は既存の管轄の問いを立てる。Pass 2 は複数 site に書かれた Why をどの単一宣言が所有するかを問い、重複・分散・総量過多の3形態を検出する。Pass 2 は監査プロンプトで定義された集合値の判定 `集約` を返す。

承認を得て書き込みを行うのはオーケストレータだけであり、それも単一スレッドで行う。これにより、並列の監査役が1つの移設先文書を奪い合うことを防ぐ。

## 4. パッケージ横断の反復を機械的に走査する

パッケージ監査を委譲した後、結果を集計する前に、解決した全ファイルへ次の走査を実行する。全ファイル集合を見られるのはオーケストレータだけであり、監査役は `維持` を件数だけで報告するため、各報告の内容を比較して反復を見つけることはできない。

```sh
for f in <resolved files>; do
  grep -hE '^[[:space:]]*(//|#|--)' "$f" \
    | sed -E 's@^[[:space:]]*(//|#|--)[[:space:]]?@@' \
    | awk -v f="$f" 'length($0) > 30 { print f "\t" $0 }'
done | sort -t$'\t' -k2 \
  | awk -F'\t' '{ n[$2]++; src[$2] = src[$2] "\n    " $1 }
                 END { for (k in n) if (n[k] > 1) print "[" n[k] "] " k src[k] }'
```

`grep` は不可欠である。これを外すとコードと空行までクラスタ化し、巨大で無意味なクラスタを1件報告する。簡略化の名目で削除しないこと。`length($0) > 30` の下限は選択したスコープに合わせて調整できる。

各クラスタは、まず管轄によって解決する。

- 反復内容の管轄が文書なら、すべての site を移設とする。文書に既に記載されている場合は短縮とする。パッケージをまたぐ概念を所有する宣言はない。
- 単一の宣言が真に概念を所有する場合に限り、メンバーが複数ファイルにまたがる集約とする。別パッケージの読者は近接性では本体を見つけられないため、各ポインタには所有宣言の名前を含める。

1つのパッケージ内で完結するクラスタは、そのパッケージの監査役へ渡す。パッケージをまたぐクラスタはオーケストレータが扱う。全メンバーが個別には正しくても、クラスタは finding である。

## 5. 判断の前に集約する

書き込みを提案する前に、監査面の全体を示す。パッケージごとに `維持 / 短縮 / 削除 / 移設 / 集約` の件数を示す。個別の findings を示すのは、矛盾と `維持` 以外の判定についてだけであり、位置・逐語のコメント・理由・完全な着地形を添える。移設先ごとの合計と、次の集計行を正確に示す。

```text
集約: <e> 件（対象コメント計 <t> 箇所 / 内訳 重複 <u> ・分散 <v> ・総量過多 <w>）
パッケージ横断の重複: <x> クラスタ（対象コメント計 <y> 箇所 / <z> パッケージにまたがる）
```

集約はメンバーごとではなく1件と数え、対象コメント数を併記する。`維持` は件数のみとする。ただしコードとの矛盾は常に個別の finding とする。対応が不要なら、日本語でその旨を述べて止める。

報告のみモードでは、全 `維持` 以外の finding を完全に表示する。各集約の全メンバーと、各移設で提案する移設先文面も含め、その後は書き込まずに終了する。自動適用で対象となる短縮・削除・集約を適用でき、確認して適用なら移設も判断できる旨を述べる。

## 6. 選択したモードに従って適用する

報告のみモードでは、この節へ進まない。

### 確認して適用

`維持` 以外の findings を影響の大きい順に処理する。各件について、証拠と before/after のコメント差分を提示する。`移設` の場合は移設先の文面も正確に提示する。その1件について番号付き選択肢を日本語で示し、ユーザーの選択を待つ。判断の際どいものをまとめて適用しないこと。

集約は集合全体に対する分割不能な1つの質問であり、メンバーごとの質問に分けない。全メンバーを示し、集約 / 維持（現状のまま）/ 別の site を本体にする / 判断を保留、の番号付き選択肢を提示する。承認を分けると Why が失われるか、重複が残る可能性がある。

承認後は、移設先の文書を先に、コードを後に書く。この順序は必須である。中断が起きても、根拠が新しい住所を持たないまま取り残されてはならない。監査役が `追記なし` と報告した場合は移設先文書を書かず、その finding を `短縮` として着地させ、コードだけを変更する。

移設先が ADR の場合、その記録の形をこちらで選ばないこと。既存 ADR-NNNN を書き換える / 新しい ADR を作る / 代わりに `docs/design` か README を使う / 今は移設しない、の番号付き選択肢を日本語で示す。承認されたら、英語の正本・隣の `.ja.md`・英日両方の ADR ログ表を揃えて更新する。パッケージ README への追記がその主張を実質的に変える場合は、続く対応として `back-prop` に言及する。

### 自動適用

対象となる短縮・削除・集約 findings を1件ごとの質問なしで書き込む。次のものは除外し、代わりに報告する。

- コメントがコードと矛盾する finding。
- オーケストレータが移設先を開いて内容の存在を確認する前の `追記なし` 移設。確認できた場合はコードのみの短縮として適用し、確認できない場合は報告する。
- `確度: high` 未満の集約。
- メンバーが複数ファイルにまたがる集約。
- 移設先文書への書き込みを伴う移設。ADR の不変性により、新規レコードか既存レコードの書き換えかは、質問しないモードでは決定できないリポジトリ方針の判断になる。

同一ファイル内で確度 high の集約は文書を書かないため対象となる。自動適用で省かれるのは質問だけであり、他のガードはすべて残る。Go の export 宣言は有効な doc comment を保ち、directive は触らず、除外ファイルはスコープ外のままとする。

## 7. 検証する

何かを書き込んだ場合のみ、この節を実行する。触れたパッケージに対して `make go-fix`、続けて `make go-lint` を実行する。Markdown の移設先へ書き込んだ場合は `make md-lint` も実行する。最後に、編集した全コメントを残滓テストに照らして読み直す。リンクを辿らない読者にとって単独で成立していなければならない。

集約後は、編集 site だけでなく、触れた全ファイルを上から下まで読む。本体 site がすべての固有事実を持ち、各ポインタから辿れることを確認する。メンバーがパッケージをまたぐ場合は、別パッケージ側からポインタを読む。

結果は日本語で報告する。stage / commit / push はしない。

## レビュー役の境界

| 道具 | スコープ | 判定 | 所管 |
| --- | --- | --- | --- |
| `impl-review` 経由の `comment-reviewer` | 差分 | 削除 / 書換 / 加筆 | 生成時の流入ゲート |
| `doc-reviewer` | `README*` / `docs/**` | 内容 findings | ドキュメント散文の品質 |
| `comment-sweep` | 在庫 | 維持 / 短縮 / 削除 / 移設 / 集約 | 内容の管轄と所有者 |
