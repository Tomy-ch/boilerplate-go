# Impl Issue

GitHub issue を、環境確保からマージ済み PR まで進める半自動パイプライン。停止箇所は判断ではなく列挙で決まる。進行・記録・検出は機械が持ち、判断はすべて人間が持つ。長い自律実行がブラックボックスにならないよう、承認した計画から外れた箇所を最後ではなくその場で表に出す。

コマンドは、このファイルだけで実行を再現できるようここに置く。自律的に更新される詳細はポインタに残す: `.makefiles/README.md`（target 一覧）、`docs/maintenance/db-worktree-pool.md`（スロットプール）、`docs/development-flow.md`（変更種別ごとのフロー）。

## 使うとき

- issue の URL / 番号を渡され、マージ済み PR まで持っていってほしいとき。
- 決定点で止まった実行の再開を頼まれたとき。

以下には使わない: issue の無い変更（`commit` + `submit-pr` を直接）、既存 diff のレビュー（`impl-review` / `test-review` / `comment-sweep`）、スキルの作成・編集（`manage-skill`）。

## 契約

| | |
| --- | --- |
| **所管** | issue → merged PR のパイプライン進行、承認済み計画と実物の突き合わせ、人間判断が要る瞬間の機械的検出 |
| **しないこと** | 未決の設計を独自に補完する / 実装判断そのもの（委譲先が持つ） |
| **開始条件** | 採択済みの issue が提示されたとき |
| **停止条件** | 下表の 5 箇所だけ。それ以外では停止せず、判断は PR コメントへ記録する |

## 停止する箇所 — 完全な一覧

このパイプラインがどこで停止するかは判断ではなく仕様である。停止するのは次の箇所だけで、それ以外では停止しない:

| # | 箇所 | 決めること |
| --- | --- | --- |
| 1 | Step 0 | 何より先に、2 回の連続した対話で 4 つのモードを決める |
| 2 | Step 3 | 書面化した計画を承認する |
| 3 | Step 4 | 行の既定値が Halt の trip-wire を判断する |
| 4 | Step 7 | 3 つの同格なレビュースキルのどれを実行するか、各々の期待効果を添えて決める |
| 5 | Step 8 | runtime 検証が失敗したとき、およびマージそのもの |

**停止とは、ターンを終えることであって、問うことではない。** 「ユーザーに何かを聞くこと」と読むと、この一覧は破りながら満たせてしまう。実際に起きる失敗は何も聞かないからである。フェーズが片付き、進捗報告を書くのが自然な流れになり、その報告のままターンが終わる — 承認は求めていないので下の禁止は発火しないのに、実行は終わり、残りの作業はユーザーの手に戻っている。一覧は問いにではなく、ターンの終わりに掛けること。

長い実行が読めるものであり続けるのは報告のおかげであり、失敗はそれをターンの最後に置くことのほうである。書いたら、同じターンの中で作業を続けること。「続けます」「次は〜します」は計画ではなくこのバグの証拠である — 次の一手を既に知っているから書けるのであり、それは何にも塞がれていないという意味だからである。告知せずにその一手を実行すること。

**塞がれていることは、停止ではない。** 実行が自分の外側へ渡した先 — CI、バックグラウンドのコマンド、委譲したエージェント — を待っていて、その受け渡しに依存しない作業が何も残っていないなら、そこでもターンは終わる。そこでは誰にも何も決めさせておらず、実行を再開させるのは答えではなく通知である。マージの手順がまさにこれの上に立っており、foreground のループではなくバックグラウンドのコマンドで待てと言っているのはそのためである。判定は、作業についての判断がユーザーの手元にあるかどうかである。あるならそれは停止であり 5 行に属する。無いならその待ちはブロックであり、同じものを待っていない作業が何も残らなくなった時点でだけターンを終える。

停止点に見えるが停止点ではない瞬間が 3 つある。未記載の停止はここから入り込む:

- **フェーズの境界。** Step 3 の承認は Steps 4–9 を覆う。計画が実行全体を列挙しており、それを承認したためである。フェーズの終了はイベントではない。seam もイベントではない。run record を書き、compaction を推奨して続行する。PR seam では Codex の明示的なユーザー入力対話で先に聞くが、その問いは作業ではなく context に関するものである。ユーザーが席を外した状態で包括的な委譲が継続している場合は、代わりに推奨を告知して続行する。
- **委譲したエージェントの完了通知。** レビューと監査は fan-out する。レポートの到着は作業を再開する箇所であり、停止する箇所ではない。
- **Step 0 で確定済みのモード。** その権限は使用済みである。レビューモードが既に許可した修正を再確認すると、ユーザーに同じことを 2 回承認させる。

停止を 1 件ずつ見れば、個々のコストは安く見え、拡散した全体コストは見えないため、毎回「聞く」が勝つ。だから上の一覧は助言ではなく閉じた一覧である。

## このスキルが持たないもの

実装判断を一切持たない。どの設計を採るか、レビュアーが正しいか、その指摘が issue に値するかを決めない。ユーザーへ回して、答えを記録する。

| 作業 | 担当 |
| --- | --- |
| コミット分割と実行 | `commit` |
| push + PR 作成/更新 | `submit-pr` |
| 変更そのもののレビュー | `impl-review` |
| テストのレビュー | `test-review` |
| 触ったファイルのコメント stock のレビュー | `comment-sweep` |
| 実装そのもの | 承認された計画に従うあなた |

3 つのレビュースキルは同格である。どれも他を呼び出さず、Step 7 でそれぞれ個別に実行可否を聞く。

## AI の変更範囲

`AGENTS.md` は AI の編集対象を `internal/` / `pkg/` / `database/` / `openapi/` に限り、それ以外 — `.github/workflows/`、`docker/`、`scripts/`、`docs/`、`.makefiles/`、ルートのドットファイル — をスコープ外としている。**このスキルの起動は、その制限を緩めるユーザーの明示指示にあたる。** このスキルは issue 汎用のドライバであり、対象面を決めるのは issue の側だからである。CI・ツールチェーン・コンテナイメージ・ドキュメントについての issue は、既定の 4 ディレクトリの中では解決できない。これは `AGENTS.md` の「Skills must not be a loophole」条項に対する、明示された抜け穴でない例外である。

緩和には境界があり、その境界は計画である:

- Step 3 の計画の **触るファイル一覧** が許可された対象面。既定の 4 ディレクトリの外にあるセンシティブなパスは、編集する**前**にそこへ現れていなければならない。glob で暗に含めるのではなく、明示的に名前を書く。
- 計画を提示するときにそれを言う。ユーザーは diff で気づくのではなく、承知のうえでセンシティブなパスを承認する — 黙ってスコープが広がる計画こそ、この条項が防ごうとしている失敗である。
- 計画に無いセンシティブなパスへ到達したら、どちらの進行モードでも停止する（Step 4 の trip-wire 1′）。聞いてから進み、対象面を広げて事後報告しない。

このスキルの実行中も保護されるもの（issue が何を要求しても触らない）:

- `AGENTS.md` / `CLAUDE.md`
- 生成物: `**/*.gen.go`、`*.sql.go`、`*_mock.go`、`**/openapi.gen.yaml`、および `docs/` 配下の生成物（`docs/openapi/**`、`docs/coverage/**`、`docs/db-schema/**`、`docs/godoc/**`、`docs/portal/docs.json`、`docs/portal/guides/**`）。`make` ターゲット経由での再生成はよい。手編集は駄目。
- エージェント自身の権限設定の `permissions.deny` 配下
- `database/migrations/**` の既存ファイル（新規 migration ファイルのみ）

## Step 0 — 4 つのモードを確認する（`ask the user explicitly` の対話を連続して 2 回）

これは 2 回の連続した呼び出しから成る 1 つの停止箇所である。何より先に最初の呼び出し、続いて 2 回目を行い、その間には何の作業もしない。最初の呼び出しは実行の振る舞いを決め、2 回目は計画フェーズのコストを決める。両者は別の問いに答えるものであり、1 回の `ask the user explicitly` 対話は 4 問が上限なので、1 回にまとめると第 5 のモードを追加する余地がなくなる。既定は明示するが、ユーザーの選択が常に優先する。

### 最初の呼び出し — 実行方針

以下の 3 問を含む 1 回の `ask the user explicitly` 対話で聞く。レビューモード、issue モード、進行モードの意味と既定値は以下のまま維持する。

**レビューモード** — レビュー指摘をどうするか。

| モード | 確定した指摘 | それ以外 |
| --- | --- | --- |
| `all` | 大きく書き換わっても適用する | — |
| `harmful`（既定） | 変更範囲内で明確に有害なものだけ適用 | issue モードへ回す |
| `issues` | 何も適用しない | issue モードへ回す |

**issue モード** — 無関係な指摘をどう追跡に載せるか。

| モード | 挙動 |
| --- | --- |
| `search`（既定） | 既存 issue を先に検索し、重複ならそこへコメント |
| `file` | 検索せず起票 |

`issues` × `file` は起票数が最大になる組み合わせ。実行前に件数を出して確認する — レビューは容易に十数件出るし、十数件の新規 issue はそれ自体がノイズ。

**進行モード** — trip-wire に当たったときどうするか。名前にトリガーを含める。このモードが支配するのは trip-wire だけで、実行全体の姿勢ではなく、他の 4 つの停止箇所には影響しない。

| モード | 挙動 |
| --- | --- |
| `record-on-tripwire`（既定） | 判断を run record へ追記して続行し、最後にそのファイルを読んで PR コメント 1 本へすべてまとめて出す |
| `halt-on-tripwire` | その trip-wire で止まって聞く |

**どちらのモードも、Step 4 で Halt と記された trip-wire を回避できない。** それらは `AGENTS.md` が無条件に人間のゲートへ残すアーキテクチャ・ドメイン・ポリシー判断である。モードが決めるのは残りの行だけ。`record-on-tripwire` は run record へ追記して続行し、`halt-on-tripwire` はそれらも聞く。ユーザーがその場にいて、スコープ拡大を最後ではなく発生時に見たい場合に後者を選ぶ。

### 2 回目の呼び出し — 計画モード

最初の呼び出しの直後に、計画モードの問いを含む 1 回の `ask the user explicitly` 対話で聞く。**各モードが何をするかだけでなく、どれだけのコストがかかるかを質問時に明示し、価格のない 3 択を並べるのではなく 1 つを推奨する。** このコストは issue の大きさにかかわらず毎回支払われる。Step 3 より前に、その変更が 1 行のドキュメント修正なのか、複数レイヤーにまたがる機能なのかを知っているのはユーザーだけである。

**計画モード** — 計画フェーズにどれだけコストをかけるか。Step 3 のどの段階を実行するかを選ぶ。どのモードも「実装者とは異なるモデルが計画を見る」という Step 3 の不変条件を満たす。変わるのは pass 数と、そのうち最上位またはそれに近い tier で実行する数である。

| モード | 段階 | コスト |
| --- | --- | --- |
| `full`（既定） | 3a + 3b + 3c | 3 pass — 起草の pass に加え、最上位またはそれに近い tier でさらに 2 pass |
| `draft-review` | 3b + 3c | 2 pass。フレーミング段階は省略 |
| `single` | 3b のみ。実装者とは異なるモデルが下書きする | 1 pass |

issue が複数レイヤーにまたがる、契約を変える、または設計判断を明記している場合は `full` を推奨する。形が固まっており詳細だけを詰めればよい場合は `draft-review`、計画が形式的なものになるほど小さい変更には `single` を推奨する。

## Run record

このパイプラインが記録するよう指示された判断は、発生時にファイルへ追記する。計画ファイルの隣、gitignore された `tmp/` 配下に、issue の名前を付けて置く。会話だけに持たせてはならない。長い実行は自身の context より長く続き、そこだけに保持したものは Step 9 で欠落を検出できないまま消える。ファイルがあれば実行も再開できる。後のセッションは、確定したモードと、それ以降に何が発火したかを回復できる。worktree をいくら調べても、この情報は分からない。

1 イベントにつき 1 行とし、何が起き、何を決めたかの両方を書く:

| 書く時点 | エントリ |
| --- | --- |
| Step 0 | 確定した 4 つのモード |
| Step 3 | 計画ファイルのパス、および 3a / 3c を実行したか |
| Step 4 | 発火したすべての trip-wire — 番号、トリガーになったもの、採った判断 |
| Step 6 | 実行しなかったすべてのゲートと、その理由 |
| Step 7 | 却下した、または提案と異なる方法で修正したすべての指摘と、その理由 |
| Step 8 | runtime 検証で覆ったものと、覆わなかったもの |

**エントリはイベント発生時に書き、最後にまとめ書きしない。** まとめ書きこそ compaction が失わせるものである。**Step 9 は実行を思い出すのではなく、このファイルを読んでコメントを組み立てる。**

## Seam

下流に必要なものがすべて既にディスク上にあるため、引き継ぐ情報がほぼ無い箇所が 2 つある:

| Seam | 下流に必要なものすべて | 既にある場所 |
| --- | --- | --- |
| Step 5 の後（実装の突合完了） | 承認済み計画、diff、ここまでに採った判断 | 計画ファイル、`git diff`、run record |
| PR を開いた後（Step 8、runtime 検証前かつ CI 実行中） | PR、ブランチ、ここまでに採った判断 | GitHub、`git`、run record |

どちらの seam でも、**まず run record を書き、次に compaction を推奨し、その上で続行する。** Step 5 の後では質問せずに推奨を告知して続行する。そこで停止しても、PR seam で得られる以上の効果は無い。PR を開いた後では、Codex の `ask the user explicitly` 対話を使い、runtime 検証の前に compaction するかを聞く。この問いは回答が来るまで進行を止めるが、作業については何も決めない。回答後は、どちらの答えでも続行する。ユーザーが席を外した状態で包括的な委譲が継続している場合は、両方の seam で質問せずに推奨を告知して続行する。自律的に完了するよう託された実行を、答える人のいない質問で止めないためである。**seam は停止箇所ではなく、5 箇所の一覧にも属さない。**

seam をこの位置に置くのは、実装フェーズだけはサブエージェントへ委譲できず、実際にオーケストレーターの window が埋まる箇所だからである。計画段階とレビューは既に委譲したエージェントで実行され、その window がオーケストレーターへ達することはない。

## Step 1 — 起動

```bash
printf '\033]0;%s\007' "<issue-number>-<slug>"   # 並行実行を見分けられるよう窓に印を付ける
gh issue view <n> --json number,title,body,labels,state,comments
```

**何か書く前に、issue 本文をベース実物と突き合わせる。** issue 本文は書かれた時点のスナップショットで、行番号・「X はまだ無い」・「Y に consumer が無い」は陳腐化する。これから切るベースに対して、本文の事実主張を 1 つずつ検証する。

その上で着手コメントを投稿する。ブランチ名・ベース commit・隔離方式、そして何より **上で見つけた食い違いすべて** を書く。issue を「着手済み」とマークすると同時に、まだ安いうちに訂正をユーザーへ渡すため。

```bash
gh issue comment <n> --body-file <file>
```

## Step 2 — 実行環境を確保する

コードに触れる前に済ませる。共有 checkout に何も落とさないため。

既存 worktree を再開する場合は、何より先に run record を読む。worktree の確認で回復できるのは作業の場所であり、作業について決めたことではない。確定したモード、発火した trip-wire、飛ばしたゲートはそのファイルにしかない。これを読まずに再開すると、判断履歴が空の状態で黙って再始動し、そのすべてが Step 9 のコメントから失われる。その後、状態を変えずに worktree のパス、`vendor/` の有無、`.gobp-db-slot` の有無を確認する。slot が無い場合、DB 作業を始める直前に `make slot-acquire` を実行する必要がある。会話を再開するだけで取得してはならない。再開時の無条件な slot 取得や DB 再初期化は禁止する。

### [Codex側の差分]

このリポジトリでは Codex の session-start hook 契約を検証できていない。そのため再開確認は `.codex/hooks.json` ではなく Step 2 に置く。skill を同期するときもこの位置を保つこと。Claude 側の session hook が同じ観測を行っても、Codex 側で再開時の DB slot 取得や DB 再初期化を起こしてはならない。

```bash
# 1. origin の live state から現行のリリース線を解決する。
BASE=$(make -s base-branch)
test -n "$BASE" || { echo "ベースブランチを解決できませんでした"; exit 1; }

# 2. 古いローカル ref ではなく、今の origin から切る。
git fetch origin "$BASE"
mkdir -p .codex/worktrees
git worktree add -b feature/<n>-<slug> .codex/worktrees/<n>-<slug> "origin/$BASE"

# 3. DB スロットをリース: 専用 DB（wt<N>_local / wt<N>_test）、API ポート 8080+N、mock-auth 2010+N。
cd .codex/worktrees/<n>-<slug> && make slot-acquire

# 4. 新規 worktree には vendor/ が無く、air は --mod=vendor でビルドするため、これが無いと serve が失敗する。
go mod vendor
```

`.codex/worktrees/` は trusted workspace の内側に置く linked worktree のコンテナである。通常作業は sandbox の書込み境界をまたがない。親 checkout からは各 linked worktree が未追跡に見えるため、このディレクトリは ignore する。親 checkout で `git clean -fdx` を実行してはならない。これらの worktree を削除し得るためである。リポジトリの local-safety rule は `git clean` を禁止している。このディレクトリを掃除するための例外を求めてはならない。

`make base-branch` は `origin` の live state を読む。この用途で他の情報は使わない。ローカルの `refs/remotes/origin/HEAD` は clone 時に一度だけ設定され、`git fetch` では更新されない。GitHub の default branch は以前のリリース線に留まり、エージェントまたは環境が渡す「main branch」ヒントもその古いローカル symref を報告しうる。いずれも警告なしに答えを返すため、世代の古いベースから切ったブランチは、期待されるファイルが無くても正しく見えうる。

`slot-acquire` が失敗を報告したら、再試行の前に `make slot-status` を見る — コマンドがエラーでもリースだけ成功していることが多い。

**スロットは自分から解放しない。片付けフェーズで解放を聞きもしない。** 握ったままのコストはほぼゼロ（リースは stale になれば自動回収される）だが、作業途中で失うと DB とポートを失う。本当に終わったかを知っているのはユーザーだけ。

ユーザーの指示が解決結果とは**異なる**リリースバージョンを指定した場合は、分岐前に聞く。意図的な
バックポート先だけは resolver には分からない。

## Step 3 — 計画を立て、そこで待つ

**不変条件: 計画を、実装者とは異なるモデルが見る。** 以下の 3 段階はそれを満たす既定の一方法であって、規則そのものではない。ここに書かれたモデル名ではなく、セッション自身のモデルから規則を読み取る。

後段のゲートは計画を再検討しない。`impl-review` / `test-review` / `comment-sweep` はいずれも完成した変更を対象にするため、その計画で issue が本当に解決するかを確認できるのはここだけである。良い下書きを作る仕事と、偏りなく下書きする仕事は別なので、選んだ計画モードに含まれる場合は別々の段階として維持する。**3 段階は停止箇所を増やさない。** 最後の承認が唯一の待機である。

**各段階のモデルは実行時に解決し、このファイルから読み取らない。** モデル id は `<family><generation>` であり、セッションは実行中のモデルを示す。そのため、このセクションに必要な 2 つの事実 — どの family が実装者のものか、どの tier がどれより上か — は Step 3 の実行時に分かる。スキルに書かれた名前は変わり続ける roster のスナップショットだが、これらの性質は変わらない。

| 段階 | 実行モデル | 成果物 | 実行するモード |
| --- | --- | --- | --- |
| 3a — フレーミング | 最上位またはそれに近い tier で、実装者とは異なる family | 計画が答えるべき問いだけ。それ以外は出さない | `full` |
| 3b — 調査と下書き | 調査と下書きに使える最も強い tier。サブエージェントとして実行 | 計画ファイル | すべてのモード |
| 3c — 計画レビュー | 3a と同じモデル。`single` では 3b が不変条件を担う | 独立セクションとして計画ファイルへ追記した指摘 | `full`、`draft-review` |

### 3a — フレーミング

`full` では Codex のエージェント委譲機構を使い、最上位またはそれに近い tier で、実装者とは異なる family のモデルへ issue 本文、Step 1 の issue ↔ ベースの食い違い、既に読んだパスを渡す。出力は**未解決の問いだけ**、すなわち計画が答えるべき問いだけとする。この段階から計画案、推奨、方向性が返ったら拒否する。この時点ではリポジトリをほとんど読んでいないため、断定できる内容は一般論にすぎない。そして、強い下書き担当へ渡した一般論は視野を広げるのではなく、アンカーになる。

### 3b — 調査と下書き

すべてのモードで、調査と下書きに最も強いモデルのサブエージェントへこの段階を委譲する。調査を、オーケストレーターが蓄積したフレーミングを一切持たないウィンドウで行うためである。issue、Step 1 の訂正、既に読んだパス、および 3a を実行した場合はその問いを渡す。「私の要約を鵜呑みにせず自分で検証しろ」と伝える。3a を実行した場合は、その**すべて**の問いに対し、どう判断したか、またはこのケースには該当しないことを必ず答えさせる。`single` では 3b が計画を見る唯一の pass なので、そのモデルは実装者とは異なる family でなければならない。

計画はチャットの発言ではなく**ファイル**にする。Step 5 が機械的に突合するため。repo の gitignore された `tmp/` 配下に置く（運用者の好みで repo 外ディレクトリへの symlink でもよい）。次のセクションが必須:

| セクション | なぜ必須か |
| --- | --- |
| 触るファイル一覧 | Step 5 が `git diff --name-only` と突合する |
| 各ステップの成果物 | 途中で止まった実行の再開・引き継ぎができる |
| 確定した選択肢と**棄却した選択肢（理由付き）** | 棄却した案を後から採ったとき trip-wire 2 が発火する |
| ゲート表 | runtime 検証の要否を計画時に固定し、後から黙って落とせなくする |

### 3c — 計画レビュー

この段階が不変条件のために必須かどうかは導出し、固定したモデル名から決め打ちしない。3b のモデルが実装者のモデルなら — 最も強い下書き tier がこのセッションを実行しているモデルでもある通常のケース —、まだ他のモデルは計画を見ていないため 3c は必須。セッションが最も強い下書き担当とは異なる family で動いており、3b のモデルが既に実装者と異なる場合は、3b の完了時点で不変条件を満たし、不変条件の観点では 3c は任意である。それでも実行する段階は計画モードに従う。`full` または `draft-review` が 3c を選んだ場合は実行し、`single` では省略する。3c は 3a と同じモデルで実行する。指摘は計画ファイルへ独立したセクションとして追記し、計画へ織り込まず、その横に並べて提示する。レビュアーが黙って計画を書き換えると、ユーザーに承認を求めるその瞬間に不一致が隠れる。承認時に各指摘を裁定するのはユーザーである。

現在の Codex surface が別モデルのエージェントを起動できないなら、選択された段階のうちどれを別モデルで実行できなかったかを明示する。`full` では、3a の問いだけという契約を守って自分で実行する。可能なら 3b を委譲し、できなければ自分で下書きする。その後、`full` または `draft-review` では 3c として独立した自己批評パスを行い、上記どおり指摘を追記する。この fallback は不変条件を満たさないと明記する。`single` は不変条件を回避する手段ではない。異なる family に一切到達できない場合は、同じモデルによる下書きへ黙って変えるのではなく、その事実を明示する。不変条件を黙って落としたり、自己批評を Step 3 全体の代わりにしたりしてはならない。

### その上で待つ

計画を提示し、**承認を待つ。承認前に実装しない。**

**その承認は Steps 4–9 を覆う。** 計画は実行全体を列挙しているため、内部の各フェーズを再承認しない。実行は次の停止箇所まで自ら進む。

## Step 4 — 実装し、5 つの trip-wire を監視する

計画が承認され、実装が始まる。決める時間と作る時間の境界であり、それを知っているのはこのスキルだけ
である。

```sh
.agents/closed-loop/marks.sh planApprovedAt 2>/dev/null || true
.agents/closed-loop/marks.sh implStartedAt 2>/dev/null || true
```

承認された計画に従う。以下は意図的に機械的なトリガーにしてある — 「判断が重要だったと**気づく**」ことに依存させるのが、まさに drift が報告されない原因だから。

| # | trip-wire | 既定 | 理由 |
| --- | --- | --- | --- |
| 1 | 計画に無いファイルを、既定の 4 ディレクトリ**内**で触る | Record | スコープは伸びたが、`AGENTS.md` が既に許可する対象面の内側 |
| 1′ | 同じことを、その**外側**（`docker/`、`scripts/`、`.github/`、`docs/`、`.makefiles/`、ルートのドットファイル）で行う | **Halt** | 計画が許可面であり、拡大はユーザーの判断 |
| 2 | 計画が棄却した案、または第三の案を採る | **Halt** | 棄却には理由があり、黙って覆すとその理由が捨てられる |
| 3 | アーキ規約由来の lint/CI 失敗（`interfacebloat` / `gocognit` / `depguard` / architest ほか） | **Halt** | これらは書式ではなく、満たすには設計が変わる |
| 4 | レビュー指摘を却下する、または提案と別の修正を採る | **Halt** | 指摘が正しくても提案された修正が有害なことがあり、単独で決める判断ではない |
| 5 | ゲートを飛ばす | Record | Step 6 が PR での明記を既に要求している |

**Halt 行はどちらの進行モードでも停止する。** これは `AGENTS.md` がアーキテクチャ・ドメイン・ポリシー判断に置く人間のゲートである。発火したら状況と推奨を提示する。`halt-on-tripwire` は Record 行にもその扱いを広げる。`record-on-tripwire` はそれらを run record へ追記して続行する。Step 9 は実行を思い出すのではなく、そのファイルを読んで、記録した判断を PR コメント 1 本へすべて出す。

### コード生成が塞がれているとき

生成系 make target は `docker compose run … make <target>-ci` の薄いラッパで、`-ci` 側は mise が入れたツールで host 実行する前提で書かれている。コンテナランタイムが使えないときは直接叩く:

```bash
make merge-dml-ci work-dir="."     # DML 連結
make sqlc-generate-ci              # sqlc
make gen-bundle-oapi-ci            # OpenAPI bundle
make gen-api-docs-ci               # docs/openapi/index.html
cd <pkg> && mockgen -source=<f>.go -destination=mock/mock_<f>.go.gen.go -package=mock_<pkg>
```

本当にコンテナが要るのは `make dump-schema` だけで、しかも migration を足したときだけ。

罠が 2 つ。`merge-dml-ci` は `go run ./cmd/` を走らせるため、クエリ生成前に Repository メソッドを足すとビルドが詰まる — 生成の間だけ実装をスタブにし、後で戻す（先に `cp` で退避）。もう 1 つ、埋め込み spec の `//go:generate` はコンテナパスを指しているので `go generate` では回らない。実パスで直接叩く:

```bash
cd internal/controller/httpstack/oapi/validator \
  && oapi-codegen --package=gen --generate=spec -o ./gen/validate.gen.go <repo>/openapi/openapi.gen.yaml
```

OpenAPI の description を 1 行変えるだけでも生成物は 3 つ動く: bundle、`docs/openapi/index.html`、その埋め込み spec。1 つでも漏らすと CI の生成物チェックが落ちる。

## Step 5 — 計画と実物を突合する

ゲートの前に行う。突合するのは:

- `git diff --name-only` ↔ 計画のファイル一覧（増えた分・触られなかった分の両方を報告）
- 実際に採った選択肢 ↔ 計画の確定/棄却リスト
- ゲート表 ↔ 実際に走らせたもの

差分を提示する。長い実行は正当な理由で drift する。問題なのは**ユーザーが見ていない drift**。drift が無ければ 1 行そう言って進む。

## Step 6 — ローカルゲート

`make go-fix` → `make go-lint` / `make go-test`。worktree が多いときは CI に任せてもよいが、**ローカル未実行であることを PR に書く**。黙っていると「検証済み」と読まれる。

runtime 検証は意図的にここに置いていない。PR ができた後（Step 8）に置くことで、CI と並行して走らせられる。

## Step 7 — レビュー

完了した変更には 3 つのレビュー対象があり、それぞれ 1 つのスキルが担当する。`impl-review` は変更そのもの、`test-review` はテスト、`comment-sweep` は触ったファイルのコメント stock を担当する。3 つは同格で、どれも他を呼び出さないため、この Step で黙って 1 つを選んではならない。

`AGENTS.md` の Review Phase Protocol に従う。実行が既に持つ文脈 — 変更した層、テストやコメントが動いたか、以前の pass が何を覆ったか — から、**各スキルの期待効果を見積もる**。その見積もりと理由を添えてスキルごとにユーザーへ聞き、承認されたものを実行する。「3 つとも実行しますか」は質問ではない。価格付けされていないコストをユーザーへ戻している。

計画、diff、Step 5 の突き合わせが揃うため、この Step が見積もりを最も安く行える箇所である。

指摘は Step 0 のレビューモードに従って処理する。自動適用してよいのは機械的に判定できるものだけ — 書式、lint 修正、コメント品質の指摘、生成物の再生成。**設計を変える修正は、レビューモード `all` であっても必ず決定点**にする。`all` が許可しているのは大きな書き換えであり、未レビューの書き換えではない。

その後、記録した trip-wire と保留した判断をまとめて 1 箇所で提示する。小出しより一括のほうが、実行全体の形が見える。

## Step 8 — PR → runtime 検証 → マージ

このステップが PR をマージしたら打刻する。ここで行うマージは、ループが後から `gh` を引くまで
他の誰も観測していない。

```sh
.agents/closed-loop/marks.sh mergedAt 2>/dev/null || true
```

先に `submit-pr` で PR を開く。ローカル検証の間に CI が回り始める。

### runtime 検証 — マージのゲート

動いているシステムに対して実 HTTP 経路を通す。どのモードでも緩められない。

```bash
make serve                                    # API は 8080+N、mock-auth は 2010+N

TOKEN=$(curl -fsS -X POST http://localhost:201N/default/token \
  -d 'grant_type=password' \
  -d 'client_id=go-boilerplate-client' \
  -d 'password=unused' \
  --data-urlencode 'username=<seeded-subject>' \
  | python3 -c 'import sys,json;print(json.load(sys.stdin)["access_token"])')

curl -s -o /dev/null -w '%{http_code}\n' -H "Authorization: Bearer $TOKEN" http://localhost:808N/v1/...
```

この手順の正本は `docs/design/auth.md` —— mock provider の標準トークンエンドポイントで、ブラウザを介さずにトークンを発行する。この抜粋と同文書が食い違うときは、文書の側が正しい。

token の subject は seed が登録した identity の `subject` 文字列でなければならない。内部の UUID ではない — シードの UUID 行はスロットのポートが発行する issuer とは別の issuer に属するため、UUID を渡すと紛らわしい 401 になる。実在する subject は DB から引く:

```bash
docker exec gobp-shared-database-1 psql -U postgres -d wt<N>_local -c \
  "select subject from <identity テーブル> where issuer = 'http://localhost:201N/default';"
```

正常系、変更が持ち込むエラー経路、そして保護された操作ならトークン無しで 401 になることを確認する。その上で **LGTM スタックのトレースを読み、リクエストが想定どおりの経路（controller → usecase → infrastructure、意図した SQL）を通ったことを確認する**。ステータスコードだけでは、そのリクエストが変更した層に届いたことの証明にならない — 間違ったが尤もらしい経路は、間違った理由で正しいステータスを返す。

**CI 緑は代替にならない。** レビューレンズも CI チェックも、DB 層で止まる静的解析やテストにすぎない。middleware がそもそもリクエストを届かせない層で、記載されたステータスコードが正しいとされてしまう。実 HTTP リクエスト 1 本で即座に決着する。

runtime 検証がどうしても実行できないときの正直な選択肢は 2 つで、第三はない。

1. まだマージしない。
2. 同じ HTTP 経路を通す統合テストを足し、それを根拠にマージする。

どちらを採ったかを明言する。

### マージ

別々の foreground sleep 呼び出しで繰り返しポーリングせずに CI を待つ。以下を 1 本の長時間コマンドとして実行し、現在の surface が対応する場合は Codex の background/yield-and-notify 機構で完了通知を 1 回だけ受ける。その機構が無い場合は、この 1 本のループを維持して blocking であることを明示する。foreground sleep-poll の連続に置き換えてはならない:

```bash
until [ "$(gh pr checks <n> --json bucket --jq '[.[]|select(.bucket=="pending")]|length')" = "0" ]; do sleep 30; done
gh pr checks <n>
```

その上で、Codex の `ask the user explicitly` 対話を使ってマージの可否を聞くこと。停止点の表の 5 行目はマージそのものをユーザーの手に置いている。緑のチェックはその問いの答えではなく前提である。CI が何と言い、runtime 検証が何を見つけたかを報告し、承認を得てから `gh pr merge <n> --merge` を実行する。

## Step 9 — 締め

issue は**手動で**クローズする。PR のベースが default branch ではなくリリースブランチのとき、自動クローズのキーワードは発火しない:

```bash
gh issue comment <n> --body-file <handover> && gh issue close <n>
```

申し送りコメントには、決めたこと・計画から想定外だったこと・意図的に手を付けなかったことを書く。

変更範囲の外にある指摘は issue モードに従って追跡へ回す。`search` では、新規起票より既存 issue への申し送りコメントを優先する — issue 数それ自体がコストで、重複は元の issue を埋もれさせる。

**起票の前に、その指摘を動いているシステムで検証する。** コードを読んだだけで導いた指摘は、静的レビューでは捕まえられない形で誤りうる — 多くの場合、読んでいた層の外側（middleware、DI 配線、DB）が既にそのケースを処理しているためである。Step 8 の runtime 段階があれば大抵は確認できる。

最後に run record を読み、上から順に辿って、すべてのエントリを PR コメント 1 本へ書く。コミットメッセージにも PR 本文にも現れていない他の自己判断も同じコメントへ記録する。停止せず記録した trip-wire はすべてここに落ち、このファイルだけがその全件を保持している。

## 二重に聞かせない委譲

サブスキルはそれぞれ自前の質問を持つ。このスキルが既にユーザーと決着させている以上、答えを payload で渡してサブスキル側のゲートを飛ばす。

| サブスキル | 渡すもの | 抑止されるもの |
| --- | --- | --- |
| `commit` | 既に提示済みのコミット分割 | 分割の承認質問 |
| `submit-pr` | レビュー実行済みであること、push の判断 | Phase 0 のレビュー確認と push 確認 |
| `impl-review` | スコープ、レビュアーモデル | Step 0 |
| `test-review` | スコープ、レビュアーモデル | スコープの質問 |
| `comment-sweep` | スコープ**と適用モード** | スコープと適用モードの質問 |

**すべての行が必須である。1 つでも欠けると、このスキルが既に決着させたゲートが復活する。** 項目ごとの確認を既定とするサブスキル — 特に `comment-sweep` — は、適用モードが渡らなければそのとおり質問する。省略は質問が始まるまで見えない。

同じことを 2 回聞くと、ユーザーは読まずに承認する癖がつく。それはこのスキルが作ろうとしている決定点そのものを無効化する。

## やること / やらないこと

- ✅ コードに触れる前に worktree とスロットを確保する。
- ✅ issue の主張をベース実物で検証し、食い違いを着手コメントに書く。
- ✅ 実装前に計画の承認を取り、Step 5 が突合できるようファイルとして残す。
- ✅ 計画を実装者とは異なるモデルに通し、そのレビュー指摘を計画へ織り込まず横に並べて提示する。
- ✅ 5 つの trip-wire を「気づくもの」ではなく機械的トリガーとして扱う。
- ✅ 列挙した 5 箇所でだけ停止し — 停止とは質問することだけでなく、ターンを終えることである —、それ以外の判断は発生時に run record へ追記する。seam では record を書いて compaction を推奨する。Step 5 seam では告知し、PR seam では Codex の明示的なユーザー入力対話で聞き、ユーザーが席を外した状態で包括的な委譲が継続している場合は両方で告知する。
- ✅ 適用モードを含め、確定済みの答えを各サブスキルへすべて渡す。
- ✅ どのゲートを走らせ、どれを走らせなかったかを明言する。
- ✅ ステータスコードだけでなくトレースを読む。
- ✅ issue を起票する前に runtime で指摘を検証する。
- ❌ HTTP 経路を一度も通していない実装コードの変更をマージする。
- ❌ CI 緑を runtime 検証として提示する。
- ❌ 設計を変える修正を、どのモードであれ自動適用する。
- ❌ フェーズ境界で承認を聞く、または委譲したエージェントの完了を停止点として扱う。
- ❌ 進捗報告でターンを終える。報告を書き、同じターンの中で続ける。
- ❌ 実行の判断を context だけに持たせる、または Step 9 のコメントを記憶から組み立てる。
- ❌ seam を停止箇所として扱う、または seam で待つ。
